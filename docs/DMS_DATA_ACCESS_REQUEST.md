# 猛士服务运营 · DMS 结构化数据只读申请

面向数字化部门的申请说明。数据表清单与逐表用途见同目录附件：

`DMS报表功能使用表.xlsx`（K 列「申请原因与用途」，L 列「所需权限」均为只读）

## 1. 申请结论

| 项 | 内容 |
|----|------|
| 申请什么 | 下列 DMS 报表对应库表（或等价只读视图 / 只读接口）的**结构化数据** |
| 权限 | **仅只读（SELECT）**，不申请 INSERT / UPDATE / DELETE，不申请执行写库过程 |
| 为什么改 | 当前用浏览器登录 DMS 后页面导出 Excel，会话保活、导出互斥、页面改版都会中断日报 |
| 数据用途 | 服务运营内部日报、超期告警、VIP 保养提醒、区域指标一览；**门店关系对应**；**门店产值分析**。不对外营销、不写回 DMS |

批准后，服务运营侧将停用（或降级为应急）DMS 页面爬虫，改为定时拉取结构化结果。

## 2. 背景

服务运营已上线三套日报，数据全部来自猛士 DMS 前台导出：

| 系统 | 本地控制台 | 现取数方式 | 北京时间 |
|------|------------|------------|----------|
| 事故车维修超期提醒 | `:9000` | 爬「维修工单总部查询」（业务类型=事故维修，近 30 天） | 10:00 / 17:00 |
| VIP 客户保养提醒 | `:9002` | 爬「保养提醒任务」全量导出，按 VIN 匹配 VIP 清单 | 09:00 |
| 区域各指标情况一览 | `:9003` | 爬「保养提醒任务」「门店库存查询」「服务管理报表」共 7 份源表 | 08:30 |

痛点：必须长期占用已登录的 Chromium；同一时刻只能有一个导出；DMS 页面或按钮文案一变，流水线就断。希望改为与前台报表**同口径**的只读结果集。

「门店关键主数据」和「服务经营报表」同样在申请范围内、同样需要：前者把门店编码、简称、售后有效、仓库与线路等关系对齐，三套日报才能按店归集；后者按店拆工时/备件/其他项目金额，分析门店产值。当前这两块仍靠人工看 DMS 或从工单里间接拼门店，申请后改为结构化取数。

## 3. 按报表说明用途

### 3.1 维修工单总部查询（现网）

事故车提醒的唯一 DMS 源。筛「事故维修」、排除已作废后：

- 识别在修（待派工 / 接车 / 维修中）与超期车辆，飞书通知门店与区域督导
- 10:00 / 17:00 出门店、区域未完工汇总；17:00 另出全国 KPI（30 天内 7 日 / 10 日完工率）

主表是 `t_se_bu_repair_order`；门店、大区、状态码、派工节点、车系为关联表。

### 3.2 门店关键主数据（需要：把门店关系做好对应）

三套日报都按「门店」归集告警和指标，必须先有一份稳定的门店维表，才能把工单、保养任务、库存、产值对到同一家店：

- 门店编码 / 简称 / 全称、售后是否有效：过滤无效店、统一店名
- 门店↔仓库、门店↔订货日历、门店↔物流线路：补全门店主数据关系，避免只靠工单上的店名对不上
- 账户资金随该查询原 SQL 带出，不是产值分析主口径；若必须裁字段，优先保证门店编码、名称、售后有效及仓库/线路对应

主表 `t_usc_mdm_org_dlr`。

### 3.3 门店库存查询（现网）

区域报表「备件库存明细」→ 常备件备库率。主表 `t_pa_bu_dlr_storage`，关联备件名称、价格、流动率、是否替换件。

### 3.4 保养提醒任务（现网，两套系统共用）

- **VIP**：任务编码、VIN、门店/区域、任务类型与状态、预约与到期、用车人/车主联系方式、首次回访、DMS 有效状态。按 VIN 匹配 VIP 后飞书通知提醒人，任务编码去重。
- **区域报表**：同一结果回填「招揽实施率」。

主表 `t_se_bu_return_visit`；首次回访看 `t_se_bu_return_visit_record`；联系人看 `t_mdm_dlr_cust_info`（仅内部跟进，不群发营销）。

### 3.5 服务管理报表（现网）

区域报表每天回填的 5 份明细（现从该页五个导出按钮拉取）：

| 明细表 | 区域报表工作表 |
|--------|----------------|
| `t_se_bu_first_maintenance_report` | 首保 |
| `t_se_bu_econdary_maintenance_report` | 二保 |
| `t_se_bu_new_insurance_report` | 新保 |
| `t_se_bu_renewal_insurance_report` | 续保 |
| `t_se_bu_no_insurance_report` | 续保（去年同期交付未新保） |

汇总表 `t_se_bu_assessment_repor` 用于和总表核对；`t_se_bu_other_statistics_repor`（NSS 等）现模板未引用，可后开。

### 3.6 服务经营报表（需要：分析门店产值）

按门店、大区、业务类型汇总已结算 / 已审核工单的台次、VIN 数，以及工时、备件、其他项目金额，用来看各店产值（台次 × 金额）。  
主数据来自 `t_se_bu_repair_order`，产值拆到工时 / 备件 / 其他项目三张明细，价格与门店系数用于金额折算。当前靠人工导出，申请后纳入结构化取数，不再新增爬虫。

## 4. 权限与安全

1. **只读**：所有表、视图、接口仅 SELECT；账号不要写权限。
2. **口径**：结果应与现行前台报表一致（可用附件 xlsx 中 F 列 SQL 作对照，不要求原样开放动态 SQL）。
3. **个人信息**：工单送修人电话、保养任务用车人/车主电话仅用于督导/门店内部跟进与飞书卡片，不对外、不写回 DMS。
4. **范围**：全国售后门店（与现总部查询账号可见范围一致）。若必须按大区裁剪，请先沟通，避免事故车全国 KPI 缺数。
5. **频率**：工作日至少各跑一轮（见上表）；允许日增量 + 当日全量补数。事故车需近 30 天工单；保养提醒需当前有效任务。

## 5. 期望交付（请数字化选型）

按实施成本从低到高，任一即可，不必三种都做：

1. **只读接口**：按「报表功能」出与前台导出同列的 JSON / CSV（最利于停爬虫）。
2. **只读视图**：按功能封装，授权 SELECT，列集对齐现导出 Excel。
3. **库表只读账号**：直接授权清单中的表，由我方按 F 列 SQL 组装（联表多，运维成本更高）。

筛选条件建议与前台一致，例如：

- 维修工单：`业务类型 = 事故维修`，到店/创建日期近 30 天，状态含在修与已完工（排除作废）
- 保养提醒：`DATA_SOURCE = 0`（与现查询一致），可先全量有效任务
- 服务管理明细：按年 + 季度（默认当年当季）
- 库存：可用库存或理论可用 ≠ 0（与现查询一致）
- 服务经营：已结算 / 已审核工单，按门店与业务类型汇总产值（工时 + 备件 + 其他项目金额）
- 门店关键主数据：`IS_ENABLE = 1` 的售后有效门店及仓库/线路对应关系
